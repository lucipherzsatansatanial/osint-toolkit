## 1. เริ่มต้นใช้งาน

### 1.1 ที่อยู่ของระบบ

| หน้า | URL | ใช้ทำอะไร |
|---|---|---|
| SOC Threat Monitor | `https://<ชื่อ service>.onrender.com/soc` | ศูนย์เฝ้าระวังภัยคุกคาม (EDR/XDR/CTI/AI agent) |
| OSINT Toolkit | `https://<ชื่อ service>.onrender.com/` | สแกนข้อมูลเปิด (domain, IP, email, brand, username) |
| คู่มือนี้ | `https://<ชื่อ service>.onrender.com/manual` | อ่านคู่มือในระบบ |
| ตรวจสถานะ | `/healthz` (ระบบทำงาน) · `/readyz` (ฐานข้อมูลพร้อม) | สำหรับผู้ดูแลระบบและ Render health check |

### 1.2 การเข้าสู่ระบบ

ระบบไม่มีหน้าล็อกอินด้วยรหัสผ่าน ใช้ **token ส่วนตัว** แทน

1. ผู้ดูแลระบบสร้างผู้ใช้ให้ในเมนู **ผู้ใช้และสิทธิ์** แล้วส่ง token ให้ทางช่องทางที่ปลอดภัย (token แสดงครั้งเดียว)
2. เปิด `/soc` ระบบจะแสดงแถบ **API key** ด้านบน → วาง token → กด **เชื่อมต่อ**
3. เมื่อเชื่อมต่อสำเร็จ ป้ายสถานะมุมซ้ายบนจะเป็น **LIVE** และกล่องด้านล่างเมนูจะแสดงชื่อ บทบาท และ tenant ของคุณ
4. ต้องการสลับผู้ใช้ กด **เปลี่ยนผู้ใช้** (ลบ token ออกจากเบราว์เซอร์นี้)

> **Break-glass key (`OSINT_API_KEY`)** คือกุญแจผู้ดูแลระดับแพลตฟอร์มสำหรับตั้งค่าเริ่มต้นเท่านั้น ใช้สร้างผู้ใช้คนแรก แล้วควรใช้ token ส่วนตัวในการทำงานจริง เพราะ audit log จะบันทึกเป็น "admin (bootstrap key)" ซึ่งไม่ระบุตัวบุคคล

### 1.3 Tenant (ลูกค้า/หน่วยงาน)

- ผู้ใช้ทั่วไปเห็นข้อมูลของ tenant ตัวเองเท่านั้น
- ผู้ใช้ระดับแพลตฟอร์ม (MSSP staff, tenant `*`) จะเห็นตัวเลือก **Tenant** ในกล่องผู้ใช้ เลือกเพื่อสลับไปดูลูกค้ารายอื่น หน้าจะโหลดใหม่และเชื่อมต่อสตรีมของ tenant นั้น
- Tenant `default` เป็นพื้นที่ demo ที่มี **ข้อมูลจำลอง** (ป้าย Telemetry: SIMULATED) ส่วน tenant ของลูกค้าจะมีเฉพาะข้อมูลจริง

### 1.4 ธีมและการนำทาง

- ปุ่ม **Dark Mode / Light Mode** ล่างสุดของเมนูซ้าย สลับธีม ระบบจำค่าไว้ในเบราว์เซอร์
- เมนูซ้ายเป็นลิงก์ไปยังแต่ละส่วนในหน้าเดียว ตัวเลขในวงกลมข้างเมนูคือจำนวนรายการ (เช่น จำนวน case, งานที่ยังไม่เสร็จ)
- เมนูที่คุณไม่มีสิทธิ์จะถูกซ่อน หรือปุ่มจะถูกปิดใช้งาน

**ลำดับเมนูตามงานประจำของ SOC Manager** (ดูภาพรวม → จัดการเหตุ → มอบหมายงาน → สืบสวน → ปรับปรุงการตรวจจับ)

| ลำดับ | กลุ่ม / เมนู | ใช้เมื่อ |
|---|---|---|
| 1 | **ภาพรวม** | เริ่มกะ ดูสถานการณ์และสิ่งที่ต้องทำก่อน |
| 2 | **Incidents (XDR)** | ดู **เหตุด้านความปลอดภัย** ที่ระบบเชื่อมโยงจากหลาย alert (มุมมองเชิงเทคนิค: โดเมน ความรุนแรง เครื่อง) |
| 3 | **Alerts** | คัดกรอง alert ทีละกลุ่ม: รับทราบ / มอบหมาย / ยกระดับ / ปิด |
| 4 | **Cases** | **แฟ้มงาน** สืบสวนและติดตามการแก้ไข: ผู้รับผิดชอบ, priority, verdict, งาน, notebook |
| 5 | **Tasks** | มอบหมายและติดตามงานของทีม |
| 6 | **รออนุมัติ** | อนุมัติคำขอตอบสนอง / สิทธิ์ AI agent (four-eyes) |
| 7 | กลุ่ม **เหตุการณ์** | Alert stream (สด) และ Log ดิบ (Events) — สลับกันได้จากปุ่มบนหัวการ์ด |
| 8 | กลุ่ม **การสืบสวน** | Query builder, Graph explorations, Notebooks, Attack Chains |
| 9 | กลุ่ม **Threat Intelligence** | Intelligence, IOC Collections, Feeds (out), Threat Landscape, Threat Map, CTI feeds สาธารณะ |
| 10 | กลุ่ม **สินทรัพย์และแหล่งข้อมูล** | Assets, Entities, EDR · Endpoints, Integrations, Intakes |
| 11 | กลุ่ม **กฎและ AI** | Rules catalog, AI Rule Assistant, AI Hunting & Enrichment, Agentic AI |
| 12 | **Offensive AI** | ท้ายเมนู แสดงเฉพาะผู้มีสิทธิ์ `offensive.read` |

- กลุ่ม 7–11 พับ/กางได้ด้วยการคลิกชื่อกลุ่ม ระบบจำสถานะไว้ในเบราว์เซอร์ และกางให้อัตโนมัติเมื่อคลิกเมนูในกลุ่ม (บนจอแคบแสดงทุกเมนูเป็นแถวเลื่อนได้)
- **Incident กับ Case คือเหตุการณ์เดียวกันในสองมุมมอง** — ทุก incident มี case ของตัวเองโดยอัตโนมัติ (และสร้าง case เองได้โดยไม่มี incident) หน้า Incidents ใช้ดูภาพเชิงเทคนิค ส่วนหน้า Cases ใช้บริหารงาน
- หัวข้อในบทที่ 4 ของคู่มือยังเรียงตามเลขเดิม ใช้ตารางนี้เพื่อหาเมนู

## 2. แนวคิดหลักของระบบ

### 2.1 เส้นทางของข้อมูล

```
แหล่ง log (EDR, firewall, AD, web, DB, AI agent)
   │  ส่งผ่าน Intake key หรือบัญชี ingest
   ▼
Ingest & normalize  ──►  เก็บเป็น Events (log ดิบ) + ค้นพบ Assets อัตโนมัติ
   │
   ▼
Detection rules (OAI / AGT / IOC / CUS)  ──►  Alert
   │
   ▼
Correlation (เครื่องเดียวกัน หรือผู้ใช้เดียวกัน ภายใน 30 นาที)  ──►  Incident = Case
   │
   ▼
Triage → Investigation → Response (ต้องอนุมัติ) → ปิด case พร้อม verdict
   │
   ▼
แจ้งเตือน (กฎแจ้งเตือน, Teams/LINE/Slack/Email/Webhook) · รายงาน · audit log
```

### 2.2 ข้อมูลจริงกับข้อมูลจำลอง

- **ข้อมูลจำลอง (SIMULATED)** สร้างโดยเครื่องจำลองในตัว เพื่อ demo และฝึกใช้งาน มีเฉพาะใน tenant `default` ไม่ถูกบันทึกลงฐานข้อมูล และไม่ถูกส่งแจ้งเตือนออกภายนอก (เว้นแต่เปิด `SOC_NOTIFY_SIMULATED`)
- **ข้อมูลจริง** มาจาก log ที่ส่งเข้ามา มีป้าย **REAL** สีเขียว ถูกบันทึกถาวรตามระยะเก็บข้อมูล
- ระบบไม่เคยรวมข้อมูลจริงกับข้อมูลจำลองไว้ใน incident เดียวกัน

### 2.3 Alert, Incident และ Case

| คำ | ความหมายในระบบนี้ |
|---|---|
| Alert | ผลจาก detection rule 1 ครั้ง (เช่น "PowerShell with encoded command" บนเครื่อง FIN-WS-014) |
| กลุ่ม Alert | alert ชื่อเดียวกันบนเครื่องเดียวกัน ถูกรวมเป็น 1 แถว พร้อมจำนวนครั้ง (Occurrences) |
| Incident | กลุ่ม alert ที่ระบบเชื่อมโยงกัน (correlation) ว่าน่าจะเป็นเหตุการณ์เดียวกัน |
| Case | ชื่อเรียกของ incident ในมุมการจัดการงาน ทุก incident คือ case ประเภท **Automatic** และ analyst สร้าง case เองได้ (ประเภท **Manual**) |
| Coordinated attack | incident ที่ครอบคลุม ≥ 2 โดเมน (เช่น email + endpoint) และมี alert ระดับ high ขึ้นไป ระบบยกระดับความรุนแรงให้ 1 ขั้น |

### 2.4 คะแนน Urgency (0–100)

`ฐานตามความรุนแรง (critical 85 / high 70 / medium 45 / low 20) + (จำนวนครั้ง − 1, สูงสุด 10) + 5 ถ้าตรงกับ CTI + 5 ถ้าอยู่ใน incident หลายโดเมน` (สูงสุด 100)
ใช้เรียงลำดับว่าควรดู alert ไหนก่อน เอาเมาส์ชี้ที่ "urgency คืออะไร?" ในหน้าจอเพื่อดูสูตร

### 2.5 การแยกหน้าที่ (Separation of duties / four-eyes)

- **การตอบสนอง** (กักกัน/ปล่อย AI agent) และ **การเพิ่ม/แก้สิทธิ์ AI agent** เป็น "คำขอ" ที่ต้องให้อีกคนอนุมัติ (เปิดเป็นค่าเริ่มต้น)
- ผู้ขอ **อนุมัติคำขอของตัวเองไม่ได้**
- เลือกเปิดได้: ผู้แก้ rule คนล่าสุดเผยแพร่ rule นั้นเองไม่ได้
- ตั้งค่าได้ที่ **Governance & AI Eval → นโยบายแยกหน้าที่**

### 2.6 ขนาดข้อมูล (SOC_SCALE)

ค่าเริ่มต้น 5 ทำให้ข้อมูลจำลองและความจุข้อมูลจริงมีขนาด 5 เท่าของค่าออกแบบเดิม (เช่น เครื่องจำลอง 70 เครื่อง, alert ในหน่วยความจำ 1,500 รายการ, ส่ง log ได้ 25,000 record ต่อครั้ง) ผู้ดูแลปรับได้ที่ตัวแปร `SOC_SCALE`

## 3. ส่วนประกอบหน้าจอที่ใช้ร่วมกัน

### 3.1 แถบสถานะด้านบน

| องค์ประกอบ | ความหมาย / การใช้งาน |
|---|---|
| **LIVE / offline** | สถานะการเชื่อมต่อสตรีมข้อมูลสด ถ้าหลุดจะเชื่อมใหม่เองทุก 3 วินาที |
| **Telemetry: SIMULATED / LIVE / SIMULATED + n real** | บอกว่าข้อมูลบนจอมาจากเครื่องจำลอง log จริง หรือทั้งสองอย่าง |
| **CTI: x/4 feeds live** | จำนวน CTI feed ที่ดึงข้อมูลได้สำเร็จ (CISA KEV, Feodo, ThreatFox, ThreatDefence) |
| **✦ ถาม AI** | เปิด SOC Assistant (ดู 3.2) — ต้องมีสิทธิ์ `ai.copilot` |
| **ต้องดำเนินการ** (กระดิ่ง) | เปิดรายการการแจ้งเตือนจากกฎ และรายการงาน/incident ที่ต้องทำ (ดู 3.3) ตัวเลขแดง = มีรายการด่วน |
| **แจ้งเตือน: …** | สถานะช่องทางแจ้งเตือนภายนอก คลิกเพื่อส่งข้อความทดสอบ (ต้องมี `integrations.manage`) |
| นาฬิกา | เวลาปัจจุบันตามเครื่องผู้ใช้ (พ.ศ.) |

### 3.2 SOC Assistant (✦ ถาม AI)

ผู้ช่วย AI ที่ตอบคำถามเกี่ยวกับข้อมูลของ tenant โดยค้นข้อมูลเองผ่านเครื่องมือแบบ **อ่านอย่างเดียว** 7 ตัว: ค้น alert, ค้น case, ดูรายละเอียด case, รัน query บน log ดิบ, ค้น Intelligence, ค้น rules catalog, ค้น assets

วิธีใช้
1. กด **✦ ถาม AI** แผงจะเปิดทางขวา
2. เลือกคำถามแนะนำ หรือพิมพ์เอง แล้วกด Enter (Shift+Enter = ขึ้นบรรทัดใหม่)
3. ใต้คำตอบจะมีป้าย 🔧 บอกว่า AI ใช้เครื่องมือใดบ้าง (เอาเมาส์ชี้เพื่อดูพารามิเตอร์)
4. ถามต่อเนื่องได้ ระบบส่งประวัติ 8 ข้อความล่าสุด

ข้อควรรู้
- AI **แก้ไขหรือสั่งการอะไรไม่ได้** ถ้าต้องตอบสนอง ให้ทำตามขั้นตอนในหน้าจอเอง
- ชื่อผู้ใช้ อีเมล และ IP ภายใน ในผลค้นหาจะถูกแทนด้วยนามแฝง (เช่น `USER_1`) ก่อนส่งให้โมเดล และแปลงกลับในคำตอบ แต่ข้อความที่คุณพิมพ์เองจะถูกส่งตามที่พิมพ์
- ถ้ายังไม่ตั้ง `ANTHROPIC_API_KEY` จะเป็น **โหมดคำสั่งพื้นฐาน** (ค้นข้อมูลตรงๆ ไม่ใช้ AI) เช่น วาง IP เพื่อค้น intelligence หรือพิมพ์ query ที่ขึ้นต้นด้วย `events |`
- ทุกคำถามบันทึกใน audit log พร้อมจำนวน token และค่าใช้จ่ายโดยประมาณ

### 3.3 กล่อง "ต้องดำเนินการ"

แบ่งเป็น 2 ส่วน
- **การแจ้งเตือนจากกฎ** — incident ที่ตรงกับ "กฎการแจ้งเตือน" ที่ตั้งไว้ กด **อ่านทั้งหมด** เพื่อทำเครื่องหมายว่าอ่านแล้ว
- **รายการที่ต้องดำเนินการ** — งานที่มอบหมายให้คุณ (งานเลยกำหนดขึ้นก่อน), incident ที่มอบหมายให้คุณ และ incident ระดับ critical ที่ยังไม่มีผู้รับผิดชอบใน 24 ชม.
- คลิกรายการเพื่อเปิด incident หรืองานนั้น ลิงก์ล่างสุดพาไปหน้ากฎการแจ้งเตือน

### 3.4 การกรอง การค้นหา และการแบ่งหน้า (ใช้เหมือนกันทุกตาราง)

- ช่องค้นหาจะค้นอัตโนมัติหลังหยุดพิมพ์ประมาณ 0.3 วินาที
- ปุ่ม **‹ ก่อนหน้า / ถัดไป ›** อยู่ล่างตาราง พร้อมบอกหน้าปัจจุบันและจำนวนรวม
- แถวที่คลิกได้ (เช่น alert ที่มี case) เมื่อคลิกจะเปิดหน้ารายละเอียด incident
- ข้อมูลส่วนใหญ่รีเฟรชเองเป็นระยะ (หน้าแรก 15 วินาที, alert/case 30 วินาที, intake/asset 60 วินาที)

### 4.2 Cases

**วัตถุประสงค์:** จัดการทุก case ทั้งที่ระบบสร้าง (Automatic) และที่ analyst สร้างเอง (Manual) (สิทธิ์ `cases.read`)

**ตาราง:** เลข case, ชื่อ case (พร้อมเครื่องที่เกี่ยวข้อง), สถานะ, Priority, Verdict, Custom fields, Tags, ผู้รับผิดชอบ, ประเภท, จำนวน alert, แก้ไขล่าสุด

**ตัวกรอง:** ค้นหา (ชื่อ/เครื่อง/tag/เลข case), สถานะ (ค่าเริ่ม: กำลังดำเนินการ), Priority, ประเภท, Tag, เรียงตาม (แก้ไขล่าสุด/สร้างล่าสุด/Priority), **ของฉัน**, **log จริง**

**ฟังก์ชัน**
- **+ New case** (`cases.create`) — สร้าง case เอง: เลือก Template (ถ้ามี), ชื่อ, รายละเอียด, Priority, ผู้รับผิดชอบ, Tags, Host ที่เกี่ยวข้อง, custom fields
  - ถ้าเลือก template ระบบจะเติม tag และสร้างงาน (Tasks) ตาม template ให้อัตโนมัติ
  - case ที่สร้างเองจะ **ไม่ถูกรวม alert อัตโนมัติ** และ **ไม่ถูกปิดเองเมื่อเงียบ**
- **Custom fields** (`governance.manage`) — กำหนดช่องข้อมูลเพิ่มของ case ต่อ tenant ได้สูงสุด 20 ช่อง ชนิด text / number / select
- คลิกแถว → เปิดหน้ารายละเอียด (หัวข้อ 5)

### 4.3 Alerts

**วัตถุประสงค์:** ดูและจัดการ alert ทุกกลุ่ม (สิทธิ์ `alerts.read`)

**ตาราง:** Occurrences (สีตามความรุนแรง), Case, วันที่ล่าสุด, Alert (ป้าย REAL, technique, rule), สถานะ, **จัดการ**, Verdict, ผู้รับผิดชอบ, Entity (เครื่อง), Urgency, Detection type, Type (tactic), Threats

**ตัวกรอง:** ค้นหา, สถานะ, ความรุนแรง, ช่วงเวลา (1 ชม./24 ชม./7 วัน/30 วัน), เรียงตาม (ล่าสุด/Urgency/Occurrences), log จริงเท่านั้น

**ปุ่มจัดการ (ต่อกลุ่ม alert)**

| ปุ่ม | สิทธิ์ | ผลลัพธ์ |
|---|---|---|
| รับทราบ | `alerts.acknowledge` | สถานะเป็น "รับทราบแล้ว" และไม่ถูกนับใน Pending |
| มอบหมาย | `alerts.assign` (มอบให้ตัวเองใช้ `alerts.acknowledge`) | ตั้งผู้รับผิดชอบ |
| ยกระดับ | `alerts.escalate` | ถ้า alert อยู่ใน case ที่เปิดอยู่: เพิ่ม priority 1 ขั้นและเปลี่ยนเป็น investigating; ถ้าไม่มี: สร้าง case ใหม่ชื่อ "[Escalated] …" แล้วเปิดให้ทันที |
| ปิด | `alerts.close` | ต้องใส่เหตุผล และเลือกได้ว่าเป็น benign; ถ้า alert เดิมเกิดซ้ำหลังปิด จะกลับเป็น "ใหม่" พร้อมป้าย "เกิดซ้ำหลังปิด" |
| เปิดใหม่ | `alerts.close` | คืนสถานะเป็นใหม่ |

**Detection type:** Built-in EDR/XDR · CTI / IOC · Offensive-AI behaviour · AI-agent policy · Custom rule

### 4.4 Events

**วัตถุประสงค์:** ค้น log ดิบที่ส่งเข้ามา (สิทธิ์ `events.read`)

- ช่องค้นหาใช้ภาษา `field:value` (ดูหัวข้อ 9.1) เช่น `kind:logon user:admin -host:DC-01`
- เลือกช่วงเวลา 5 นาที – 7 วัน แล้วกด **ค้นหา**
- **กราฟแท่ง** แสดงจำนวน event ตามเวลา: สีน้ำเงิน = log จริง, สีเทา = ข้อมูลจำลอง
- **ตาราง:** เวลา, ชนิด (kind), เครื่อง, คำอธิบายที่อ่านง่าย (เช่น "svc.backup logged on to DC-01 from 10.10.1.0") และแหล่ง (intake)
- คลิกแถวเพื่อดูข้อมูลดิบ (JSON)
- log จริงถูกเก็บตาม `SOC_RAW_RETENTION_DAYS` (ค่าเริ่ม 7 วัน)

### 4.5 Threat Landscape

**วัตถุประสงค์:** ดูแนวโน้มภัยคุกคาม (สิทธิ์ `alerts.read`) เลือกช่วงเวลา alert ได้ 24 ชม./7 วัน/30 วัน

| กราฟ/ตาราง | แหล่งข้อมูล |
|---|---|
| Malware prevalence | จำนวน IOC ต่อวันต่อ malware family จาก ThreatFox (export "recent" ครอบคลุมไม่กี่วัน) |
| MITRE technique prevalence | alert ของ tenant นี้ แยกตามเทคนิค ตามช่วงเวลา |
| Known exploited vulnerabilities ต่อสัปดาห์ | จำนวน CVE ที่ CISA เพิ่มใน KEV ย้อนหลัง 12 สัปดาห์ และผู้ผลิตที่พบมาก |
| CVE ที่ถูกใช้โจมตีจริงล่าสุด | CVE ล่าสุดใน KEV พร้อมลิงก์ NVD และป้าย ransomware |
| Threats ที่พบใน alert | threat ที่ระบุชื่อได้ (framework/malware/CVE) ใน alert ของ tenant พร้อมจำนวน IOC ที่เกี่ยวข้องใน ThreatFox |

> หมายเหตุ: ไม่ใช่สถิติระดับโลก แสดงเฉพาะ feed สาธารณะและข้อมูลของ tenant นี้

### 4.5.1 Threat Map

**วัตถุประสงค์:** ภาพรวมแบบจอ wall display ว่าโครงสร้างพื้นฐานที่อยู่เบื้องหลัง alert ของเรามาจากประเทศใด อะไรถูกโจมตีมากที่สุด และฐานข้อมูล IOC ของเรามีอะไรบ้าง (สิทธิ์ `alerts.read`) เลือกช่วง 7 หรือ 30 วัน รีเฟรชเองทุก 60 วินาทีขณะเปิดดู

| ส่วน | แสดงอะไร | แหล่งข้อมูล |
|---|---|---|
| Incident · IOC unique | จำนวน incident ในช่วงที่เลือก และจำนวน IOC ไม่ซ้ำในฐานข้อมูล Intelligence (ไม่รวม CVE) | incident ของ tenant, Intelligence |
| Attack trend | จำนวน incident ใหม่รายวัน 30 วัน | incident ของ tenant |
| ประเทศต้นทางของโครงสร้างพื้นฐาน | 10 ประเทศที่ alert มาจากมากที่สุด + จำนวน alert ที่ระบุประเทศไม่ได้ | ดูหมายเหตุด้านล่าง |
| ลูกโลก | เส้นจากประเทศต้นทาง 10 อันดับมายังประเทศของเรา (`SOC_HOME_COUNTRY`, ค่าเริ่ม TH) เส้นส้ม = 3 อันดับแรก ความหนาตามจำนวน alert · **ลากเพื่อหมุน** | เหมือนข้างบน |
| ภาพเคลื่อนไหว | **ดาวหาง** วิ่งจากประเทศต้นทางเข้าหาไทยตามอัตราส่วนจำนวน alert · **ดาวหางสว่างสีตามความรุนแรง** (แดง critical / ส้ม high / เหลือง medium / เขียว low) = alert ที่เพิ่งเข้ามาทางสตรีมสด พร้อมวงคลื่นตอนปล่อยและตอนถึงเป้า · ลูกโลกส่ายช้าๆ (หยุด 3 วินาทีหลังผู้ใช้ลาก) · ตัวเลข แท่งกราฟ และวงแหวนค่อยๆ ขยายเมื่อรีเฟรช · ปิดอัตโนมัติถ้าตั้ง "ลดการเคลื่อนไหว" ใน OS | สตรีม alert สด |
| Live feed | 5 alert ล่าสุดที่รู้ประเทศต้นทาง: ความรุนแรง, ประเทศ → ไทย, ชื่อ alert, เครื่อง, ป้าย REAL ถ้ามาจาก log จริง | สตรีม alert สด |
| วงแหวน 5 วง | สัดส่วน alert ตาม MITRE ATT&CK tactic 5 อันดับแรก | alert ของ tenant |
| Asset ที่ถูกโจมตีมากที่สุด | 8 เครื่องที่มี alert มากที่สุด (H = จำนวน alert ระดับ high/critical) | alert ของ tenant |
| Top 5 ประเทศที่โฮสต์ botnet C2 | ประเทศที่ตั้งของ C2 server ทั่วโลก | abuse.ch Feodo Tracker |
| IOC Database | จำนวน IOC 5 ประเภทแรก (ipv4, domain, url, hash …) | Intelligence (CTI feeds + IOC ของ tenant) |

> **ประเทศคือที่ตั้งของโครงสร้างพื้นฐาน (server / proxy / VPN / C2) ไม่ใช่สัญชาติหรือตัวตนของผู้โจมตี** ผู้โจมตีมักเช่าเซิร์ฟเวอร์ต่างประเทศ ห้ามนำไปสรุปว่า "ประเทศ X โจมตีเรา"

**ระบบรู้ประเทศได้อย่างไร (ไม่เดา):** ใช้ `src_country` ของ log ก่อน — log แบบ ECS อ่านจาก `source.geo.country_iso_code` อัตโนมัติ, log แบบ native ใส่ฟิลด์ `src_country` (รหัส ISO 2 ตัว เช่น `CN`) ได้ เช่นจาก Logstash `geoip` — ถ้าไม่มี จะดูว่า IP ปลายทาง/IOC อยู่ใน Feodo Tracker หรือไม่ ถ้าไม่มีทั้งสองอย่างจะนับเป็น "ระบุประเทศไม่ได้" ข้อมูลจำลองใน tenant `default` สุ่มประเทศขึ้นเอง (มีข้อความ "ส่วนใหญ่เป็นข้อมูลจำลอง" กำกับ)

### 4.6 Query builder

**วัตถุประสงค์:** ค้นและสรุปข้อมูลด้วยภาษาแบบ pipe (สิทธิ์ `query.run`)

1. เขียน query ในกล่อง (กด **วิธีเขียน** เพื่อดูสรุปไวยากรณ์ หรือดูหัวข้อ 9.2)
2. เลือกช่วงเวลา แล้วกด **▶ Run query** (หรือ Ctrl+Enter)
3. ผลแสดงเป็นตาราง พร้อมจำนวนแถว จำนวนที่สแกน และเวลาที่ใช้
4. **บันทึก query** — เก็บไว้ใช้ซ้ำ แสดงในรายการ "Query ที่บันทึกไว้" ด้านขวา (คลิกเพื่อรัน, × เพื่อลบ)
5. **Export CSV** — ดาวน์โหลดผลลัพธ์ (กันสูตร Excel อันตรายให้อัตโนมัติ)

ระบบตีความ query เอง ไม่รันโค้ดหรือ regex ที่ผู้ใช้ส่งมา จึงปลอดภัย

### 4.7 Notebooks

**วัตถุประสงค์:** บันทึกการสืบสวนแบบ Markdown แชร์ในทีม tenant เดียวกัน (อ่าน `notebooks.read`, เขียน `notebooks.write`)

- **+ New notebook** — สร้าง notebook ใหม่
- โหมด **แก้ไข / แสดงผล** — รองรับหัวข้อ (`#`), ตัวหนา, ตัวเอียง, รายการ, โค้ด, ลิงก์ http(s)
- **บันทึก** — ถ้ามีคนอื่นบันทึกก่อนคุณ ระบบจะแจ้ง "notebook was changed by …" ให้โหลดใหม่ก่อน เพื่อไม่ให้เขียนทับกัน
- **ย้ายไปถังขยะ / กู้คืน** — ดูถังขยะได้ที่แท็บ **ถังขยะ**
- notebook ที่สร้างจากหน้า case จะผูกกับ case นั้น (แสดงเลข INC และลิงก์กลับ)

### 4.8 Intelligence

**วัตถุประสงค์:** ค้น IOC จากทุกแหล่งในที่เดียว และดูว่าเคยเห็นใน log ของเราหรือไม่ (อ่าน `threatintel.read`)

- ค้นได้หลายค่าพร้อมกัน (บรรทัดละค่า หรือคั่นด้วย `,`) รองรับรูปแบบ defang เช่น `evil[.]com`, `hxxp://` กด **ค้นหา** หรือ Ctrl+Enter
- กรองตามชนิด (ipv4, domain, url, hash, cve, user_agent ฯลฯ), แหล่ง, ความเชื่อมั่น
- ค่าที่ไม่พบในฐานข้อมูลจะแสดงใต้ช่องค้นหา
- **ตาราง:** TLP, ชนิด, Indicator, Conf. (ความเชื่อมั่น 0–100), แหล่ง (ลิงก์อ้างอิงถ้ามี), Threat/รายละเอียด, พบครั้งแรก, **เห็นใน tenant (7 วัน)** = จำนวน log และ alert ที่พบค่านี้ พร้อมเครื่องและเวลาล่าสุด
- **+ เพิ่ม IOC ของเรา** (`threatintel.curate`) — ดู 4.9

แหล่งข้อมูล: abuse.ch ThreatFox, abuse.ch Feodo Tracker, CISA KEV, ThreatDefence agentic-attack-detections และ IOC ของ tenant

**🛡 ตรวจกับ VirusTotal** (`threatintel.enrich`) — ใช้ค่าที่อยู่ในช่องค้นหา (hash md5/sha1/sha256, URL, domain, IP สูงสุด 10 ค่า) ไปค้นใน VirusTotal API v3
- แต่ละค่าแสดง: ผล (อันตราย / น่าสงสัย / ไม่พบการตรวจจับ / ไม่มีข้อมูล), จำนวน engine ที่ตรวจพบ เช่น **5/66**, reputation, ป้ายภัย (threat label), engine ที่ตรวจพบ, รายละเอียดตามชนิด (ชื่อไฟล์/ชนิด/ขนาด, ASN/ประเทศ, registrar/วันจดทะเบียน, หมวดหมู่), วันวิเคราะห์ล่าสุด และลิงก์ **เปิดใน VirusTotal**
- บอกบริบทภายในด้วยว่าค่านั้น **อยู่ใน Intelligence ของเรา** หรือ **เห็นใน log/alert ของ tenant ใน 7 วัน** หรือไม่
- **ค้นอย่างเดียว ไม่อัปโหลดไฟล์** — ระบบไม่มีฟังก์ชันส่งไฟล์ให้ VirusTotal เพราะไฟล์ที่อัปโหลดจะดาวน์โหลดได้โดยลูกค้า premium ของ VirusTotal (เสี่ยงข้อมูลลูกค้ารั่วและขัด PDPA) ให้ใช้ hash แทน
- **ไม่ส่งข้อมูลภายใน** — IP ภายใน (private/reserved), โดเมน `.local` `.corp` `.internal` `.lan` ฯลฯ, ชื่อเครื่องที่ไม่มีจุด, URL ที่ฝังชื่อผู้ใช้/รหัสผ่าน และโดเมนใน `VT_BLOCK_DOMAINS` จะถูกปฏิเสธก่อนออกจากเซิร์ฟเวอร์
- **โควตา** — ค่าเริ่มต้นตามบัญชีฟรี 4 ครั้ง/นาที และ 500 ครั้ง/วัน (ปรับด้วย `VT_RATE_PER_MIN`, `VT_DAILY_QUOTA`) ผลถูกเก็บใน cache 1 ชม. ค่าที่ค้นซ้ำจึงไม่เสียโควตา (ป้าย "จาก cache") ถ้าเกินโควตาระบบบอกเวลาที่ต้องรอ
- **ส่งให้ VirusTotal สแกนใหม่…** (เฉพาะ URL, ต้องมี `threatintel.curate` เพิ่ม) — ใช้เมื่อ VirusTotal ยังไม่มีข้อมูล URL นั้น ระบบจะถามยืนยันเพราะ **URL จะถูกเปิดเผยต่อชุมชน VirusTotal** ห้ามส่ง URL ที่มี token ข้อมูลลูกค้า หรือระบบภายใน
- ทุกการค้นและการส่งสแกนบันทึกใน audit log (`soc.vt_lookup`, `soc.vt_scan_url`) พร้อมจำนวนครั้งที่เรียก API จริง
- ถ้าตั้ง `VT_API_KEY` แล้ว **AI Threat Enrichment** (4.25) และโมดูล **Domain / IP** ของ OSINT Toolkit จะดึงผล VirusTotal มาประกอบให้อัตโนมัติ (ผู้ใช้ต้องมี `threatintel.enrich` สำหรับ enrichment)

### 4.9 IOC Collections

**วัตถุประสงค์:** จัด IOC ของเราเป็นชุดตามแคมเปญหรือ incident และใช้ตรวจ log ด้วย rule **IOC-001** (สิทธิ์ดู `threatintel.read`, แก้ `threatintel.curate`)

- **+ New collection** — ตั้งชื่อและรายละเอียด
- เลือก collection ทางซ้าย → ตารางขวาแสดง: ชนิด, Observable, Threat, Valid from, Valid until, Kill chain, รายละเอียด, TLP, ปุ่ม **Revoke / เปิดใช้อีกครั้ง**
- **นำเข้า / เพิ่ม IOC** — เปิดหน้าต่างเพิ่ม IOC:
  - วาง IOC บรรทัดละรายการ หรือเลือก **นำเข้าจากไฟล์ (.txt / .csv)** (ใช้คอลัมน์แรก ข้ามหัวคอลัมน์ value/indicator/ioc)
  - ตั้ง TLP, ความเชื่อมั่น, วันหมดอายุ, Threat/แคมเปญ, ความรุนแรงของ alert, Tags, รายละเอียด, Collection, Kill chain phase

- **สร้าง telemetry report** — เลือก 7/30/90 วัน แล้วดูว่า IOC ใดในชุดเคยปรากฏใน log/alert ของ tenant บนเครื่องไหน และ **ดาวน์โหลด CSV** ได้ (ต้องมี `soc.export`)
- IOC ที่ revoke หรือหมดอายุแล้วจะหยุดสร้าง alert ทันที
- ข้อจำกัด: IOC หนึ่งค่าอยู่ได้ collection เดียว

### 4.11 Feeds (out)

**วัตถุประสงค์:** ให้ไฟร์วอลล์หรือ CTI platform อื่นดึง IOC ของเราไปใช้ (สิทธิ์ดู `threatintel.read`, สร้าง/แก้ `threatintel.curate`)

- **+ New feed:** ชื่อ, รายละเอียด, ชนิด indicator, แหล่ง, รูปแบบ (**STIX 2.1** / **Text** บรรทัดละรายการ / **CSV**), TLP สูงสุดที่ส่งออก, ความเชื่อมั่นขั้นต่ำ, การเรียง, จำนวนสูงสุดต่อครั้ง, เปิดใช้งาน

**ตั้งค่า FortiGate:** Security Fabric → External Connectors → Threat Feeds → IP Address หรือ Domain Name → URI of external resource = Feed URL (ใช้ feed แบบ Text)

### 4.16 Rules catalog

**วัตถุประสงค์:** ดู detection rule ทั้งหมด สถิติ 7 วัน และเปิด/ปิดราย tenant (ดู `rules.read`, เปิด/ปิด `rules.publish`)

- **KPI:** Rules ทั้งหมด, เปิดใช้งาน, Rules ที่สร้างเอง, Alerts 7 วัน, ถูกปฏิเสธ (verdict false positive/benign) 7 วัน, Active IOCs

- **กรองตามชนิด log ที่ rule ต้องใช้** — ✓ = มี log ชนิดนั้นเข้าระบบแล้ว; ปุ่ม **เฉพาะที่มี log** แสดงเฉพาะ rule ที่ใช้งานได้จริงตอนนี้
- **การ์ด rule:** รหัส, ชื่อ, ความรุนแรง, หมวด, technique/tactic, ไฟล์ส่งออก (KQL/SPL), log ที่ต้องใช้, alerts 7 วัน, ถูกปฏิเสธ, **Quality** (สัดส่วน alert ที่ไม่ถูกปฏิเสธ), สวิตช์เปิด/ปิด

**วัตถุประสงค์:** คิวคำขอที่ต้องให้อีกคนอนุมัติ (ดู `cases.read` / `agents.read`)

### 4.18 Tasks

**วัตถุประสงค์:** มอบหมายและติดตามงานของทีม (ดู `soc.read`, สร้าง/แก้ `cases.update`, มอบหมายให้ผู้อื่น `cases.assign`)

- **+ สร้างงาน:** ชื่องาน, รายละเอียด, ผู้รับผิดชอบ (ผู้ใช้ใน tenant เดียวกัน), สถานะ, กำหนดส่ง, Incident ที่เกี่ยวข้อง
- สถานะ 5 แบบ: **รอดำเนินการ · รอข้อมูล · กำลังทำ · เสร็จแล้ว · ยกเลิก** — เปลี่ยนจาก dropdown ในตารางได้ทันที
- กำหนดส่งที่เลยแล้วแสดงเป็นสีแดง "เลยกำหนด"
- คลิกชื่องานเพื่อแก้ไข เพิ่ม **บันทึกความคืบหน้า** และดูประวัติการเปลี่ยนแปลง
- ตัวกรอง: ค้นหา, สถานะ, **เฉพาะของฉัน**
- รับงานที่ยังไม่มีเจ้าของมาเป็นของตัวเองได้ด้วย `cases.update`
- **สร้างงานจากแผนตอบสนอง** — ในหน้า case ส่วน "แผนตอบสนอง" กด **สร้างงานจากแผนนี้** ระบบสร้างงานจากทุกขั้นที่ยังไม่เสร็จ (ข้ามขั้นที่มีงานชื่อเดียวกันอยู่แล้ว) กำหนดส่งตามขั้น: กักกัน 4 ชม. · กำจัด 1 วัน · กู้คืน/แจ้ง 3 วัน (ตาม PDPA 72 ชม.) · บทเรียน 14 วัน มอบหมายให้ผู้อื่นพร้อมกันได้ถ้ามี `cases.assign`
- **งานจำลอง (ป้าย "จำลอง")** — ใน tenant `default` ที่มีข้อมูลจำลอง ระบบมี "ทีม SOC จำลอง" (บัญชีลงท้าย `.demo`) เปิดงานให้ incident จำลองระดับ high/critical จากแผนตอบสนองของ incident นั้น (สูงสุด 3 งานต่อ incident) และขยับสถานะเองตามเวลา: รอดำเนินการ → กำลังทำ → เสร็จแล้ว บางงาน "รอข้อมูล" และงานที่ยังไม่เริ่มจะถูกยกเลิกเมื่อ incident ปิด งานจำลอง **เก็บในหน่วยความจำเท่านั้น ไม่บันทึกลงฐานข้อมูล แก้ไขไม่ได้** และไม่มีใน tenant ของลูกค้า

- **หยุดชั่วคราว / เล่นต่อ** — หยุดการเลื่อนเพื่ออ่าน

### 4.22 Agentic AI

**วัตถุประสงค์:** ตรวจจับและไล่ล่าภัยจาก AI agent ภายในองค์กร (ดู `agents.read`)

| ส่วน | รายละเอียด |
|---|---|
| **Agent inventory** | agent, เจ้าของ, เครื่อง, จำนวน scope (+shell), จำนวนการเรียกเครื่องมือ, จำนวนครั้งที่ถูกปฏิเสธ, **Risk** (0–100 พร้อมเหตุผลเมื่อชี้เมาส์), สถานะ (normal/contained/unregistered/retired) |
| ปุ่ม **Contain / Release** | ขอกักกันหรือปล่อย agent (`respond.execute`) → เข้าคิวรออนุมัติ (ถ้าเปิด four-eyes) |
| ปุ่ม **Retire / นำกลับมาใช้** | ปลด agent ออกจากการใช้งาน (`agents.deploy`) กิจกรรมหลัง retire ถูกบล็อกและแจ้ง AGT-011 |
| **Detection rules** | rule AGT-001 ถึง AGT-012 พร้อม MITRE ATT&CK/ATLAS และจำนวนครั้งที่ทำงาน |
| **Agent audit log (live)** | บันทึกการทำงานของ agent แบบสด: prompt, tool call, process, network, auth และผลการตัดสิน (allowed/denied/blocked) — คลิกแถวเพื่อเปิด session |
| **Session** | ไทม์ไลน์ของ session และ **process tree** ของคำสั่งที่ agent สั่ง |
| **Threat hunting** | ค้น audit log ด้วย `field:value` (ดู 9.1) พร้อมปุ่มค้นหาสำเร็จรูป (denied/blocked, shell, secrets, egress, prompt injection, any detection) |

การเพิ่ม/แก้สิทธิ์ agent ทำผ่าน API `POST /api/soc/agents/register` (`agents.edit`) และต้องได้รับอนุมัติก่อน (ดู 4.17)

### 4.23 Offensive AI

**วัตถุประสงค์:** ตรวจจับเครื่องมือโจมตีที่ขับเคลื่อนด้วย AI agent เช่น ARTEX, AntiFox, Cairn, PentAGI, HexStrike, CyberStrikeAI, Strix, Hermes Agent, Agent Zero (สิทธิ์ `offensive.read` — Analyst ขึ้นไป; Viewer ไม่เห็นเมนูนี้ แต่ alert จาก rule OAI ยังแสดงในหน้า Alerts ตามปกติ)

- **Framework cards** — สรุปแต่ละ framework จุดที่ควรเฝ้าระวัง และ rule ที่ครอบคลุม
- **Behaviour rules** OAI-001 ถึง OAI-014 — เน้นพฤติกรรม ทนต่อการเปลี่ยน user-agent/banner มากกว่าการจับ IOC
- **Live detections** — alert จาก rule กลุ่มนี้แบบสด
- **Hunting query library** — query สำเร็จรูปสำหรับ Microsoft Defender XDR / Sentinel (KQL), Splunk (SPL), Sigma กด **คัดลอก** หรือ **ดาวน์โหลด**

### 4.24 AI Rule Assistant

**วัตถุประสงค์:** สร้าง custom rule (CUS-xxx) ด้วย AI หรือเขียนเอง (สิทธิ์ `rules.edit`; เผยแพร่ `rules.publish`; ย้อนเวอร์ชัน `rules.rollback`)

1. **ให้ AI ร่างกฎ** — พิมพ์สิ่งที่ต้องการตรวจจับเป็นภาษาไทย/อังกฤษ หรือ **เขียนกฎเอง**
2. ระบบตรวจรูปแบบ (กัน regex อันตรายแบบ ReDoS), รันกรณีทดสอบ (ควรเจอ/ไม่ควรเจอ), และ **ย้อนทดสอบกับข้อมูลล่าสุด** ว่าจะเกิด alert กี่ครั้ง
3. แสดงผลเป็น Sigma / KQL / SPL / JSON แก้ JSON ได้แล้วกด **ทดสอบอีกครั้ง**
4. **บันทึกเป็น draft** — rule ใหม่จะเป็นเวอร์ชัน 1 สถานะปิด; การแก้ rule ที่มีอยู่จะเป็น **draft** โดยเวอร์ชันที่ใช้งานยังทำงานต่อ
5. หัวหน้าทีมกด **เผยแพร่ draft** / **เปิดใช้** / **ปิด** ในรายการ "กฎที่สร้างเอง"
6. **ย้อนเวอร์ชัน…** — เลือกเวอร์ชันเก่า ใส่เหตุผล ระบบบันทึกเป็นเวอร์ชันใหม่ (เก็บ 20 เวอร์ชันล่าสุด)

### 4.25 AI Hunting & Enrichment

- **Natural Language Hunting** (`ai.hunt`) — พิมพ์คำถามภาษาธรรมชาติ เช่น "หาเซิร์ฟเวอร์ที่ติดต่อ AI API ของจีนในชั่วโมงที่ผ่านมา" AI แปลงเป็นเงื่อนไขค้นหา แล้ว **ระบบค้นเองในข้อมูลของเรา** (ข้อมูลไม่ถูกส่งให้ AI ทั้งหมด) มีคำถามตัวอย่างให้กด
- **AI Threat Enrichment** (`ai.enrich`) — ใส่ IP, domain, URL, hash, CVE หรือ user-agent แล้วกด **วิเคราะห์** ระบบรวมข้อมูลจาก CTI, log ภายใน และ VirusTotal (ถ้าตั้งค่าและมีสิทธิ์ `threatintel.enrich`) แล้วให้ AI สรุปความเสี่ยงและสิ่งที่ควรทำ
- ปุ่ม 👍/👎 ใต้คำตอบ AI — ให้คะแนนคุณภาพ (ใช้ในหน้า Governance)

### 4.26 Attack Chains

**วัตถุประสงค์:** เชื่อมหลาย incident ที่มีเครื่อง บัญชี IP ผู้โจมตี หรือ AI agent ร่วมกันภายใน 24 ชม. ให้เห็นเส้นทางการโจมตีทั้งหมด (สิทธิ์ `cases.read`)
- การ์ดแต่ละ chain แสดง incident ที่เกี่ยวข้องเรียงตามขั้น MITRE tactic
- **เล่าเส้นทางด้วย AI** (`ai.copilot`) — ให้ AI สรุปเรื่องราวการโจมตีและสิ่งที่ควรทำ

### 4.27 Threat Intelligence (CTI)

แสดงข้อมูลล่าสุดจาก feed จริง 3 แหล่ง (สิทธิ์ `threatintel.read`)
- **CISA KEV** — CVE ที่ถูกใช้โจมตีจริง พร้อมกำหนดแก้ไขและป้าย ransomware
- **Botnet C2 — Feodo Tracker** — IP ของ C2 server พร้อม malware และสถานะ online/offline
- **IOCs — ThreatFox** — IOC ล่าสุดพร้อม malware และความเชื่อมั่น
- **รีเฟรช** — ดึงข้อมูลใหม่ทันที (ปกติดึงทุก 15 นาที)

## 5. หน้า Incident / Case (รายละเอียด)

เปิดได้จากทุกตารางที่คลิกได้ หรือ URL `/soc#inc-<เลข>` ปิดด้วยปุ่ม **ปิด**

### 5.1 ส่วนหัวและข้อมูล case

- หัวข้อ: เลข, ชื่อ, ความรุนแรง, ผู้ใช้, tactics
- ป้าย **Automatic / Manual** และเวลาเห็นครั้งแรก/ล่าสุด, ผู้สร้าง
- **Priority** และ **Tags** — แก้แล้วกด **บันทึก** (`cases.update`)
- **Impact** — เครื่องที่เกี่ยวข้อง พร้อมตั้ง Criticality 0–5 (`assets.manage`)
- **Custom fields** ของ tenant

### 5.2 แท็บ

| แท็บ | เนื้อหา |
|---|---|
| **Details** | กราฟความเชื่อมโยง (โดเมน → incident → เครื่อง), ไทม์ไลน์ alert, workflow, แผนตอบสนอง, AI SOC Copilot |
| **Alerts** | alert ทั้งหมดใน case: เวลา, ความรุนแรง, ชื่อ, technique, เครื่อง, ผู้ใช้, rule, CTI |
| **Tasks** | งานที่ผูกกับ case นี้ + **สร้างงานใน case นี้** |
| **Events** | log ดิบของเครื่องและผู้ใช้ใน case ช่วง 1 ชม. ก่อน–หลังเหตุการณ์ |
| **Notebooks** | notebook ของ case + **สร้าง notebook ของ case นี้** (มีโครงร่าง "สิ่งที่พบ/ขั้นตอนต่อไป" ให้) |

### 5.3 Workflow (บันทึกการทำงาน)

| ช่อง | สิทธิ์ที่ต้องใช้ |
|---|---|
| สถานะ: open → investigating | `cases.update` |
| สถานะ: resolved / false positive / closed หรือเปิด case ที่ปิดแล้วใหม่ | `cases.close` |
| Verdict: True positive / False positive / Benign / ยังสรุปไม่ได้ | `cases.update` |
| ผู้รับผิดชอบ: มอบให้ผู้อื่น | `cases.assign` (รับเองใช้ `cases.update`) |
| บันทึกของ analyst | `cases.update` |

- **บันทึก** — ทุกการเปลี่ยนแปลงลงประวัติใน case และ audit log พร้อมชื่อผู้ใช้จริง
- **รายงาน (HTML/PDF)** (`soc.export`) — เปิดรายงาน incident พิมพ์เป็น PDF ได้จากเบราว์เซอร์ มีสรุป AI (ถ้ามี) และตารางป้องกันสูตร Excel
- incident อัตโนมัติที่เปิดอยู่และไม่มี alert ใหม่ 30 นาทีจะถูกปิดเอง (สถานะ closed (idle)) ส่วนที่ analyst เปลี่ยนสถานะแล้วจะไม่ถูกแตะ

### 5.4 แผนตอบสนอง (Response plan)

- ขั้นตอนตาม NIST: กักกัน (contain) → กำจัด (eradicate) → กู้คืน (recover) → แจ้ง (notify) → บทเรียน (lessons) สร้างจาก rule และเทคนิคที่พบ
- ติ๊กเมื่อทำเสร็จ (`cases.update`) แถบความคืบหน้าจะขยับ
- **นาฬิกา PDPA 72 ชม.** — ถ้ามีสัญญาณข้อมูลส่วนบุคคลรั่วไหล ระบบแสดงเวลาที่เหลือในการแจ้ง สคส. ตามมาตรา 37(4)

### 5.5 AI SOC Copilot

- **สรุปด้วย AI** (`ai.copilot`) — สรุปเหตุการณ์ ระดับความรุนแรง ไทม์ไลน์ ขั้นการโจมตี และขั้นตอนตอบสนองแบ่ง **ทันที / วันนี้ / ติดตาม** พร้อมทีมที่รับผิดชอบ และคำถามที่ควรตรวจต่อ
- **สร้างใหม่** — สรุปใหม่เมื่อมีข้อมูลเพิ่ม
- **ตรวจการอ้างอิง (grounding)** — ระบบตรวจว่าเครื่อง IP CVE rule ที่ AI อ้างถึงมีอยู่จริงในข้อมูล ถ้าไม่มีจะเตือน "ข้อมูลที่ตรวจสอบไม่ได้"
- **ถามต่อ** — พิมพ์คำถามเกี่ยวกับ incident นี้ หรือกดคำถามสำเร็จรูป (เช่น "ต้องแจ้ง สคส. ตาม PDPA หรือไม่")
- ถ้า AI ใช้ไม่ได้ ระบบใช้ **สรุปแบบกฎ** แทนและบอกเหตุผล

## 7. OSINT Toolkit

**วัตถุประสงค์:** สแกนข้อมูลเปิด (Open-Source Intelligence) อย่างถูกต้องตามกฎหมาย (สแกน `osint.scan`, ดูประวัติ `osint.history`, ส่งออก `osint.export`)

### 7.1 โมดูล

| โมดูล | ตรวจอะไร |
|---|---|
| **Domain** | DNS (A, AAAA, MX, NS, TXT, SOA, CAA), RDAP/WHOIS, certificate transparency (subdomain), HTTP และ TLS, ชื่อเสียงจาก VirusTotal (ถ้าตั้ง `VT_API_KEY`) |
| **IP Address** | reverse DNS, เจ้าของ IP ผ่าน RDAP, ตำแหน่ง/ASN (ipinfo ถ้าตั้งค่า), ชื่อเสียงจาก VirusTotal (ถ้าตั้ง `VT_API_KEY`) |
| **Email** | ความปลอดภัยอีเมลของโดเมน (SPF, DMARC, DKIM), Gravatar, การรั่วไหล (Have I Been Pwned ถ้าตั้งค่า) |
| **Brand / Lookalike** | โดเมนเลียนแบบ (typosquatting, homoglyph, สลับ TLD รวม .co.th/.in.th) และคำในใบรับรอง (CT log) |
| **Username** | ตรวจว่ามีชื่อผู้ใช้นี้บนแพลตฟอร์มสาธารณะหรือไม่ — **เป็นเพียงความเป็นไปได้** ชื่อซ้ำกันไม่ได้แปลว่าเป็นคนเดียวกัน ต้องตรวจยืนยันเอง |

### 7.2 ขั้นตอนการสแกน

1. เลือกโมดูลทางซ้าย
2. กรอก **เป้าหมาย (Target)**, Brand keyword (เฉพาะโมดูล Brand ไม่บังคับ)
3. กรอก **ผู้ตรวจสอบ**, **เลขอ้างอิงเคส**, **วัตถุประสงค์** และเลือก **ฐานทางกฎหมาย PDPA** (consent, contract, legal obligation, vital interest, public task, legitimate interest, own asset)
   - โมดูล **Email** และ **Username** เกี่ยวกับข้อมูลส่วนบุคคล จึงบังคับกรอกวัตถุประสงค์และฐานทางกฎหมาย
4. กด **เริ่มสแกน** → ผลแสดงเป็นการ์ดแยกตามหัวข้อ
5. **Export JSON** ดาวน์โหลดผล · **Raw JSON** ดูข้อมูลดิบ

### 7.3 ประวัติการสแกน

- **ส่งออก CSV** (เห็นเฉพาะผู้มี `osint.export`) — ประวัติทั้งหมดของ tenant และบันทึก audit log ว่าใครส่งออก

## 8. ขั้นตอนการทำงานตามสถานการณ์ (Playbook การใช้งาน)

### 8.1 Triage alert ประจำกะ (Analyst)
1. เปิด **ภาพรวม** ดู Pending alerts และตาราง Alerts (เรียงตาม urgency แล้ว)
2. ไปที่ **Alerts** กรอง "ใหม่" + "critical + high"
3. แต่ละแถว: **รับทราบ** → ถ้าน่าสงสัย **ยกระดับ** (ได้ case) → ถ้าไม่เป็นอันตราย **ปิด** พร้อมเหตุผลและเลือก benign
4. ดู **ต้องดำเนินการ** (กระดิ่ง) เพื่อตามงานที่ได้รับมอบหมาย

### 8.2 สืบสวน case
1. เปิด case → **สรุปด้วย AI** อ่านภาพรวมและสิ่งที่ควรทำก่อน
2. แท็บ **Alerts** และ **Events** ดูหลักฐาน · **Graph explorations** ไล่ความเชื่อมโยงต่อ
3. ค้น IP/โดเมนที่เกี่ยวข้องใน **Intelligence**
4. **สร้าง notebook ของ case นี้** บันทึกสิ่งที่พบ · สร้างงานใน case
5. ติ๊กขั้นตอนใน **แผนตอบสนอง** · ตั้ง **Verdict** · ปิด case (ต้องมี `cases.close`)

### 8.3 รับลูกค้า / แหล่ง log ใหม่ (Admin/Lead)
1. **Entities** → สร้าง entity โหมด **monitor** ก่อน
2. **Intakes** → สร้าง intake เลือกรูปแบบ log ผูก entity → เก็บ key
3. ตั้งค่า log shipper ส่งไปที่ `/api/soc/intake` (ดูหัวข้อ 10)
4. ตรวจ Valid / Invalid / Warning ใน Intakes และดู log ใน **Events**
5. ดู **Rules catalog → เฉพาะที่มี log** ว่า rule ไหนใช้งานได้
6. เมื่อพร้อม เปลี่ยน entity เป็น **automatic**

### 8.4 บล็อก IOC ที่ไฟร์วอลล์ (Analyst + Lead)
1. **IOC Collections** → สร้าง collection ตามแคมเปญ → นำเข้า IOC (TLP:GREEN)
2. ระบบเริ่มตรวจ log ด้วย IOC-001 ทันที และ **สร้าง telemetry report** ดูว่าเคยโดนมาแล้วหรือไม่
3. **Feeds (out)** → สร้าง feed แบบ Text เลือกแหล่ง "IOC ของ tenant" ชนิด ipv4/domain → ใส่ URL ใน FortiGate

### 8.5 วงจรชีวิตของ custom rule
1. Analyst: **AI Rule Assistant** ร่าง → ทดสอบ → บันทึกเป็น draft
2. Lead: ตรวจผลทดสอบ → **เผยแพร่ draft**
3. ดู Quality ใน **Rules catalog** ถ้าเกิด false positive มาก → แก้เป็น draft ใหม่ หรือ **ย้อนเวอร์ชัน**

### 8.6 กักกัน AI agent ที่มีพฤติกรรมผิดปกติ
1. ผู้มี `respond.execute` กด **Contain** ใน Agentic AI ใส่เหตุผล → เกิดคำขอ
2. อีกคนที่มี `respond.approve` เปิด **รออนุมัติ** → อนุมัติ → ระบบกักกันทันที
3. เมื่อแก้ไขแล้ว ขอ **Release** และอนุมัติแบบเดียวกัน

### 8.7 ตั้งการแจ้งเตือนเข้า LINE กลุ่ม SOC (Admin)
1. ตั้ง `SOC_NOTIFY_LINE_TOKEN` และ `SOC_NOTIFY_LINE_TO` ใน Render Environment
2. กด **แจ้งเตือน: …** เพื่อส่งข้อความทดสอบ
3. **กฎการแจ้งเตือน** → สร้างกฎ "critical จาก log จริง" ช่องทาง ในระบบ + LINE

## 9. ภาษาค้นหา (Query / Hunting syntax)

### 9.1 แบบ `field:value` (ใช้ใน Events และ Threat hunting)

| รูปแบบ | ความหมาย | ตัวอย่าง |
|---|---|---|
| `field:value` | ฟิลด์มีคำนี้ (ไม่สนตัวพิมพ์เล็กใหญ่) | `user:admin` |
| `-field:value` | ไม่มีคำนี้ | `-host:DC-01` |
| คำเปล่า | ค้นในคำอธิบาย | `nmap` |
| `rule:*` | (Threat hunting) record ที่มี detection ใดก็ได้ | `rule:* kind:tool_call` |

หลายเงื่อนไขคั่นด้วยช่องว่าง = ต้องตรงทุกข้อ

### 9.2 Pipe query (ใช้ใน Query builder และ SOC Assistant)

```
events                                  ← แหล่ง: events (log ดิบ) หรือ alerts
| where kind == "logon" and user contains "adm"
| where bytes > 1000000 or port in (22, 3389)
| sort by ts desc
| count by host, user                   ← สรุปจำนวน (จบสายข้อมูล)
| fields ts, host, user                 ← เลือกคอลัมน์
| limit 100
```

| ตัวดำเนินการ | ความหมาย |
|---|---|
| `==` `!=` | เท่ากับ / ไม่เท่ากับ (ไม่สนตัวพิมพ์) |
| `contains` `!contains` | มี / ไม่มีข้อความ |
| `startswith` `endswith` | ขึ้นต้น / ลงท้าย |
| `>` `>=` `<` `<=` | เปรียบเทียบตัวเลข |
| `in (a, b)` `!in (a, b)` | อยู่ / ไม่อยู่ในรายการ |
| `exists` `!exists` | มีค่า / ไม่มีค่า |

- `and` มีลำดับก่อน `or` ไม่รองรับวงเล็บ
- ข้อความใส่ `"..."` หรือ `'...'` · ฟิลด์ซ้อนใช้จุด เช่น `record.cmdline`
- ไม่ใส่ `limit` จะแสดง 200 แถวแรก

**ฟิลด์ที่พบบ่อยใน log ดิบ:** `ts`, `kind` (process/http/net/logon/db/dlp/tool_call/prompt/network/auth), `host`, `user`, `image`, `cmdline`, `src_ip`, `dest_ip`, `dest`, `dst_host`, `uri`, `ua`, `status`, `port`, `bytes`, `dest_host`, `src_host`, `logon_type`, `event_id`, `agent`, `tool`, `description`, `source`

**ตัวอย่างที่ใช้บ่อย**
- เครื่องที่ logon มากที่สุด: `events | where kind == "logon" | count by dest_host | limit 10`
- ส่งข้อมูลออกปริมาณมาก: `events | where kind == "net" and bytes > 100000000 | sort by bytes desc`
- alert จาก log จริงระดับ critical: `alerts | where simulated == false and severity == "critical"`

## 10. การส่ง log เข้าระบบ

### 10.1 สองวิธี

| วิธี | ใช้เมื่อ | Endpoint | การยืนยันตัว |
|---|---|---|---|
| **Intake key** (แนะนำ) | ทุกแหล่ง log ถาวร | `POST /api/soc/intake` | header `X-Intake-Key: ik_…` |
| **บัญชี ingest** | สคริปต์/ระบบเดิม | `POST /api/soc/ingest?format=…` | header `X-API-Key: <token ของบัญชี ingest>` |

บัญชีบุคคล (analyst/lead/admin) ส่ง log ไม่ได้

### 10.2 รูปแบบ log ที่รับ

| รูปแบบ | ใช้กับ |
|---|---|
| `native` | JSON/NDJSON รูปแบบกลางของระบบ (kind: process, http, net, logon, db, dlp และ AI-agent audit) |
| `ecs` | Elastic Common Schema (Winlogbeat, Packetbeat, Filebeat, Auditbeat, Logstash/Fluent Bit ที่แปลงเป็น ECS) |
| `defender` | Microsoft Defender for Endpoint Advanced Hunting (DeviceProcessEvents, DeviceNetworkEvents, DeviceLogonEvents) |
| `access_log` | Web server access log (Apache/Nginx combined) ระบุ `?host=` |
| `auto` | ให้ระบบตรวจรูปแบบเอง |

ทุกรูปแบบใส่ `src_country` (รหัสประเทศ ISO 2 ตัวของ IP ฝั่งตรงข้าม) ได้ เพื่อให้ Threat Map แสดงประเทศต้นทางของ log จริง — ECS อ่านจาก `source.geo.country_iso_code` ให้เอง

ยังไม่รองรับ FortiGate syslog โดยตรง — ต้องแปลงผ่าน Logstash/Fluent Bit เป็น ECS ก่อน

### 10.3 ตัวอย่าง

```bash
curl -X POST https://<service>.onrender.com/api/soc/intake \
  -H "X-Intake-Key: ik_xxxxxxxx" \
  --data-binary @events.ndjson
```

```json

```

## 11. ความเป็นส่วนตัว ความปลอดภัย และ PDPA

- **Token และ key ทุกชนิด** (ผู้ใช้, intake, feed) เก็บเฉพาะค่า SHA-256 และแสดงครั้งเดียว
- **Audit log แบบ hash chain** — ทุกการกระทำสำคัญบันทึกชื่อผู้ใช้จริง และตรวจได้ว่ามีการแก้ย้อนหลังหรือไม่
- **แยกข้อมูลราย tenant** — ทุกการอ่านกรองตาม tenant ผู้ใช้ทั่วไปเลือก tenant อื่นไม่ได้
- **AI กับข้อมูลส่วนบุคคล** — ชื่อผู้ใช้ อีเมล IP ภายใน ถูกแทนด้วยนามแฝงก่อนส่งให้ Claude (ปิดได้ด้วย `SOC_AI_REDACT=off`) และตรวจการอ้างอิงในคำตอบ
- **ระยะเก็บข้อมูล** — ข้อมูล SOC 90 วัน, log ดิบ 7 วัน, OSINT 90 วัน (ปรับได้) incident ที่ยังเปิดอยู่ไม่ถูกลบ
- **OSINT** ต้องระบุวัตถุประสงค์และฐานทางกฎหมายสำหรับข้อมูลส่วนบุคคล
- **นาฬิกา 72 ชม.** สำหรับการแจ้งเหตุละเมิดข้อมูลส่วนบุคคลต่อ สคส.
- **CSV ทุกไฟล์** ป้องกัน formula injection (ค่าที่ขึ้นต้นด้วย `= + - @` จะถูกใส่ `'` นำหน้า)
- **จำกัดอัตราการเรียก** — การอ่าน 300 ครั้ง/นาที/IP, การเขียนและสแกน 30 ครั้ง/นาที/IP, feed 60 ครั้ง/นาที/IP
